In plain terms: this checks whether each project's backlog is growing faster than the team can clear it, and flags contributors assigned to more than one project at once — the same check a resource manager runs on a company's portfolio, applied here to public GitHub data.
Real data, pulled live: every number on this page came from a live call to the GitHub REST/Search API on July 12–13, 2026 — fetch_portfolio.sh hits /search/issues three ways per repo (open issues, open PRs, issues closed in the trailing 30 days), and capacity_model.py turns the raw JSON into a demand/capacity rollup. No ServiceNow SPM tenant is public to pull from, so five real, high-traffic Microsoft open-source repos (vscode, TypeScript, playwright, terminal, monaco-editor) stand in for "projects" in a technology portfolio — but the mechanics are identical to what SPM's Resource, Demand, and Capacity modules compute from real work-item and assignment data: open backlog vs. recent throughput, and contributors assigned across more than one project at once.
One honest note on the model: "capacity" here is a throughput proxy — issues closed in the trailing 30 days, not verified staffing hours or FTE counts, since GitHub doesn't expose those. That's a real limitation of open data, and it's exactly the kind of gap the actual job (this model is auditioning for) exists to close: getting resource managers to report clean, current allocation data in the first place. The demand, backlog, and cross-repo overlap numbers are exact.

Why an Open-Source Portfolio Models Enterprise Capacity Planning
Same mechanics as ServiceNow SPM's Resource, Demand, and Capacity modules
▾

Strip away the tooling and every resourcing problem comes down to the same three things: how much work is waiting, how fast the team is actually getting through it, and whether any one person is quietly carrying too much of it. Enterprise PMOs track this with dedicated software — ServiceNow SPM does it through Demand records, Resource Plans, and Capacity Plans — but the underlying shape of the problem doesn't change based on the tool.

A portfolio of actively maintained GitHub repositories has the same shape: open issues and pull requests are the demand backlog, recent issue-closure velocity is the capacity/throughput signal, and a contributor assigned to open work in more than one repository at once is exactly the "resource conflict" a PMO analyst would flag between two concurrent projects.

  • Demand — open issues + open pull requests per repo, pulled live, not estimated
  • Capacity — issues closed in the trailing 30 days, a real (if imperfect) throughput proxy
  • Conflict — a contributor holding open assignments in 2+ repos at the same time

The Dataset & Sourcing

Demand — PRs

Capacity — Throughput
is:issue is:closed closed:>=2026-06-13
Issues closed in the trailing 30 days — the closest a public API gets to a team's real clearance rate.

Portfolio: microsoft/vscode, microsoft/TypeScript, microsoft/playwright, microsoft/terminal, and microsoft/monaco-editor — five actively maintained repos sharing a contributor pool, the same way an org's engineers rotate across concurrent projects.

The Python Capacity Model
Demand, capacity, utilization ratio, and cross-repo conflict detection
▾

Four small, real calculations turn the raw API responses into a portfolio rollup:

Demand (Backlog)
backlog = open_issues + open_prs
Everything currently sitting in the queue for a repo — the same rollup a PMO dashboard shows per project.
Capacity (Throughput)
capacity = closed_issues_30d or 1
Guards against divide-by-zero for slow-moving repos — TypeScript closed just 27 issues in 30 days against a 5,054-item backlog.
Utilization Ratio
ratio = round(backlog / capacity, 2)
Backlog months, in effect — how many 30-day cycles it would take to clear the current queue at the current pace.
Conflict Detection
shared = {login: repos for login, repos in map.items() if len(repos) >= 2}
Any contributor with open assignments in 2+ repos — flagged as an allocation risk, ranked by total open load.
